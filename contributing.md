# Contributing

Additions, corrections and removals are all welcome, for any product that fits the scope.

## Before you open a pull request

Check the entry against the three scope rules in [What counts](README.md#what-counts):

1. Dialogue is generated by a language model at runtime.
2. There is a romantic or courtship frame.
3. State carries between messages.

Something can be excellent and still not fit. Character chat clients with no relationship progression belong in [awesome-ai-companion](https://github.com/DasterProkio/awesome-ai-companion). Hand authored visual novels belong in a visual novel list.

The list stays work safe. Projects and apps whose main draw is explicit content will be closed, and this is a scope decision rather than a judgement about quality.

## Entry format

Open source, under **Open source projects**, **Engines and frameworks** or **Backends and models**:

```
- [Name](repo url) `stars` `language` `license` - What it is, then what is interesting about it.
```

Shipped products, under **Apps**:

```
- [Name](url) `iOS` `Android` `Web` - What it is, then what is interesting about it.
```

Tag every platform the product ships on. Put the entry in the subsection its documented mechanics justify: a match or roster flow plus a failure or progression mechanic makes it a dating simulator, persistent one-character state without failure makes it a companion, everything else is a character chat platform. A yes in the mechanics matrix needs the listing sentence in the pull request. The matrix is generated from the [data repo](https://github.com/ai-dating-simulators/data), so send the row change there.

Rules for the description:

- One or two sentences. Say what the thing does, not that it is great.
- Describe mechanics in concrete terms. "Characters stop replying after low quality messages" is useful. "Deeply immersive experience" is not.
- No superlatives, no marketing copy, no claims you cannot check by opening the project.
- Do not compare an entry unfavourably to another entry. Describe what it does and let readers compare.

Keep the list alphabetical inside a section only where it already is. Otherwise the ordering is roughly by how much of the genre the entry covers, and a maintainer may move your entry.

## Corrections

Star counts, licences and platforms go stale. A pull request that only fixes those is welcome and will be merged quickly.

If an entry is dead, unmaintained or has changed enough that the description is wrong, open an issue with what you found. Dead projects are not automatically removed, since a stalled project can still be worth reading, but the description should say so.

## Adding a mechanic to the glossary

The glossary documents systems that appear in more than one project under more than one name. To add one, say which projects implement it and what the different names for it are. A mechanic that only one product has is not a glossary entry, it belongs in that product's description.
